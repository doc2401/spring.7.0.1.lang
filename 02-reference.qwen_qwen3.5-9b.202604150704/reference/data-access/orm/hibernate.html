    Hibernate

    我们从 Spring 环境下的 Hibernate 覆盖开始，利用它来演示 Spring 整合对象关系映射器（ORM）的方法。本节详细涵盖了许多问题，并展示了不同的 DAO 实现和事务界定变体。这些模式中的大多数可以直接转换到所有其他支持的 ORM 工具中。本章的后续部分则涵盖其他 ORM 技术，并展示简要示例。

    自 Spring Framework 7.0 起，Spring 需要 Hibernate ORM 7.x 以支持 Spring 的 HibernateJpaVendorAdapter。

    org.springframework.orm.jpa.hibernate 包取代了之前的 orm.hibernate5：现在可与 Hibernate ORM 7.1+ 配合使用，与 HibernateJpaVendorAdapter 紧密集成，同时支持 Hibernate 原生的 SessionFactory.getCurrentSession() 风格。

    SessionFactory 在 Spring 容器中的设置

    为避免将应用程序对象绑定到硬编码的资源查找，您可以将资源（例如 JDBC DataSource 或 Hibernate SessionFactory）定义为 Spring 容器中的 bean。需要访问资源的应用程序对象通过 bean 引用接收对这些预定义实例的引用，如下一节中 DAO 定义所示。

    下面的 XML 应用程序上下文定义摘录展示了如何在其之上设置 JDBC DataSource 和 Hibernate SessionFactory：

    <beans>

	<bean id="myDataSource" class="org.apache.commons.dbcp.BasicDataSource" destroy-method="close">
		<property name="driverClassName" value="org.hsqldb.jdbcDriver"/>
		<property name="url" value="jdbc:hsqldb:hsql://localhost:9001"/>
		<property name="username" value="sa"/>
		<property name="password" value=""/>
	</bean>

	<bean id="mySessionFactory" class="org.springframework.orm.jpa.hibernate.LocalSessionFactoryBean">
		<property name="dataSource" ref="myDataSource"/>
		<property name="mappingResources">
			<list>
				<value>product.hbm.xml</value>
			</list>
		</property>
		<property name="hibernateProperties">
			<value>
				hibernate.dialect=org.hibernate.dialect.HSQLDialect
			</value>
		</property>
	</bean>

</beans>

    从本地 Jakarta Commons DBCP BasicDataSource 切换到 JNDI 定位的 DataSource（通常由应用服务器管理）仅涉及配置，如下例所示：

    <beans>
	<jee:jndi-lookup id="myDataSource" jndi-name="java:comp/env/jdbc/myds"/>
</beans>

    您还可以使用 Spring 的JndiObjectFactoryBean / <jee:jndi-lookup>访问位于 JNDI 的SessionFactory，以检索并暴露它。然而，在 EJB 上下文之外，这通常并不常见。

    Spring 还提供了LocalSessionFactoryBuilder变体，可无缝集成@Bean风格的配置和程序化设置（不涉及FactoryBean）。

    `LocalSessionFactoryBean` 和 `LocalSessionFactoryBuilder` 均支持后台引导，Hibernate 初始化将在给定的引导执行器（例如 `SimpleAsyncTaskExecutor`）上与应用引导线程并行运行。在 `LocalSessionFactoryBean` 中，这通过 `bootstrapExecutor` 属性提供。对于程序化的 `LocalSessionFactoryBuilder`，存在一个接受引导执行器参数的重载 `buildSessionFactory` 方法。

    这种原生的 Hibernate 设置还可以暴露一个 JPA EntityManagerFactory，以便在原生 Hibernate 访问之外进行标准的 JPA 交互。有关详细信息，请参阅用于 JPA 的原生 Hibernate 设置。

    基于普通 Hibernate API 实现 DAO

    Hibernate 有一个称为上下文会话的功能，在此功能中，Hibernate 本身为每个事务管理一个当前的Session。这大致相当于 Spring 对每个事务一个 HibernateSession的同步。相应的 DAO 实现类似于以下示例，该示例基于纯 Hibernate API：

    • Java

    • Kotlin

    public class ProductDaoImpl implements ProductDao {

	private SessionFactory sessionFactory;

	public void setSessionFactory(SessionFactory sessionFactory) {
		this.sessionFactory = sessionFactory;
	}

	public Collection loadProductsByCategory(String category) {
		return this.sessionFactory.getCurrentSession()
				.createQuery("from test.Product product where product.category=?")
				.setParameter(0, category)
				.list();
	}
}
    class ProductDaoImpl(private val sessionFactory: SessionFactory) : ProductDao {

	fun loadProductsByCategory(category: String): Collection<*> {
		return sessionFactory.currentSession
				.createQuery("from test.Product product where product.category=?")
				.setParameter(0, category)
				.list()
	}
}

    此风格与 Hibernate 参考文档和示例类似，不同之处在于将 SessionFactory 保存在实例变量中。我们强烈建议采用这种基于实例的设置方式，而不是使用 Hibernate 的 CaveatEmptor 示例应用程序中的老式 static HibernateUtil 类。（一般来说，除非绝对必要，否则不要将任何资源保存在 static 变量中。）

    前面的 DAO 示例遵循了依赖注入模式。如果针对 Spring 的 HibernateTemplate 进行编码，它将非常适合集成到 Spring IoC 容器中。您也可以在纯 Java 中（例如在单元测试中）设置此类 DAO。为此，请实例化它并调用 setSessionFactory(..) 方法传入所需的工厂引用。作为 Spring bean 定义，该 DAO 将类似于以下内容：

    <beans>

	<bean id="myProductDao" class="product.ProductDaoImpl">
		<property name="sessionFactory" ref="mySessionFactory"/>
	</bean>

</beans>

    这种 DAO 风格的主要优势在于它仅依赖于 Hibernate API，无需导入任何 Spring 类。从非侵入性角度来看，这颇具吸引力，并且可能让 Hibernate 开发者感觉更加自然。

    然而，DAO 抛出普通的 HibernateException（这是 unchecked 异常，因此无需声明或捕获），这意味着调用者只能将异常视为一般性的致命错误——除非他们希望依赖 Hibernate 自身的异常层次结构。在不将调用者与实现策略绑定的情况下，无法捕获特定原因（例如乐观锁失败）。这种权衡对于那些高度基于 Hibernate、不需要任何特殊异常处理的应用程序来说可能是可以接受的，或者两者皆是。

    幸运的是，Spring 的 LocalSessionFactoryBean 支持 Hibernate 的 SessionFactory.getCurrentSession() 方法，适用于任何 Spring 事务策略，即使使用 HibernateTransactionManager 也能返回当前由 Spring 管理的交易性 Session。该方法的默认行为仍然是返回与当前 JTA 事务关联的 Session（如果有的话）。无论您使用的是 Spring 的 JtaTransactionManager、EJB 容器管理的事务（CMTs）还是 JTA，此行为均适用。

    总之，您可以基于纯 Hibernate API 实现 DAO，同时仍能参与由 Spring 管理的事务。

    声明式事务划分

    我们建议您使用 Spring 的声明式事务支持，它允许您用 AOP 事务拦截器替换 Java 代码中的显式事务界定 API 调用。您可以通过在 Spring 容器中使用 Java 注解或 XML 来配置此事务拦截器。这种声明式事务功能使您能够将业务服务与重复的事务界定代码分离开来，专注于添加业务逻辑，而这正是应用程序的真正价值所在。

    在继续之前，如果您尚未阅读，我们强烈建议您阅读 声明式事务管理。

    您可以使用 @Transactional 注解标注服务层，并指示 Spring 容器查找这些注解，为这些已标注的方法提供事务语义。以下示例展示了如何操作：

    • Java

    • Kotlin

    public class ProductServiceImpl implements ProductService {

	private ProductDao productDao;

	public void setProductDao(ProductDao productDao) {
		this.productDao = productDao;
	}

	@Transactional

    程序化事务界定

    您可以在应用程序的更高层面界定事务，其建立在跨越任意数量操作的底层数据访问服务之上。此外，对周围业务服务的实现也不存在限制。它仅需一个 Spring PlatformTransactionManager。同样，后者可以来自任何地方，但最好通过 setTransactionManager(..) 方法作为 bean 引用提供。同时，productDAO 也应通过 setProductDao(..) 方法进行设置。以下代码片段对在 Spring 应用程序上下文中定义事务管理器和业务服务，以及业务方法实现的示例：

    Spring 的TransactionInterceptor允许在回调代码中抛出任何受检的应用程序异常，而TransactionTemplate则仅限于在回调中抛出未检查异常。如果发生未检查的应用程序异常，或者应用程序通过设置TransactionStatus将事务标记为仅回滚，TransactionTemplate将触发回滚。默认情况下，TransactionInterceptor的行为方式相同，但允许针对每个方法配置可定制的的回滚策略。

    事务管理策略

    TransactionTemplate 和 TransactionInterceptor 都将实际的事务处理委托给一个 PlatformTransactionManager 实例（对于 Hibernate 应用程序，该实例可以是使用底层 ThreadLocal Session 的 HibernateTransactionManager（针对单个 Hibernate SessionFactory），也可以是委托给容器 JTA 子系统的 JtaTransactionManager）。您甚至可以使用自定义的 PlatformTransactionManager 实现。从原生 Hibernate 事务管理切换到 JTA（例如，当您的应用程序的某些部署需要分布式事务时）仅需配置即可。您可以将 Hibernate 事务管理器替换为 Spring 的 JTA 事务实现。由于它们使用通用的事务管理 API，因此事务界定和数据访问代码无需更改即可工作。

    对于跨越多个 Hibernate 会话工厂的分布式事务，您可以将JtaTransactionManager作为事务策略与多个LocalSessionFactoryBean定义相结合。每个 DAO 随后会获得一个特定的SessionFactory引用，该引用被传递到其对应的 bean 属性中。如果所有底层的 JDBC 数据源都是事务容器类型，那么只要使用JtaTransactionManager作为策略，业务服务就可以在不加特殊考虑的情况下，跨越任意数量的 DAO 和任意数量的会话工厂来界定事务。

    Both HibernateTransactionManager 和 JtaTransactionManager 均允许与 Hibernate 配合进行适当的 JVM 级缓存处理，无需容器特定的事务管理器查找或 JCA 连接器（如果您不使用 EJB 来发起事务）。

    HibernateTransactionManager 可以将特定 DataSource 的 Hibernate JDBC Connection 导出为纯 JDBC 访问代码。此功能允许在完全无需 JTA 的情况下，对混合使用 Hibernate 和 JDBC 的数据访问进行高级事务界定，前提是您仅访问一个数据库。HibernateTransactionManager 会自动将 Hibernate 事务暴露为 JDBC 事务，如果您已通过 LocalSessionFactoryBean 类的 dataSource 属性使用 DataSource 配置了传入的 SessionFactory。或者，您可以通过 HibernateTransactionManager 类的 dataSource 属性显式指定需要暴露事务的 DataSource。

    对于 JTA 风格的实际资源连接的懒加载，Spring 提供了针对目标连接池的相应 DataSource 代理类：请参阅LazyConnectionDataSourceProxy。这对于 Hibernate 只读事务特别有用，因为这些事务通常可以从本地缓存处理，而无需访问数据库。

    比较容器管理和本地定义的资源

    您可以在无需更改任何一行应用程序代码的情况下，在容器管理的 JNDI SessionFactory 和局部定义的 SessionFactory 之间进行切换。是将资源定义保留在容器中还是在应用程序内部局部定义，主要取决于您使用的交易策略。与 Spring 定义的局部 SessionFactory 相比，手动注册的 JNDI SessionFactory 不提供任何优势。通过 Hibernate 的 JCA 连接器部署 SessionFactory 提供了参与 Jakarta EE 服务器管理基础设施的附加价值，但除此之外并未增加实际价值。

    Spring 的事务支持不依赖于容器。当配置为除 JTA 以外的任何策略时，事务支持也可在独立或测试环境中运行。特别是在单数据库事务的典型情况下，Spring 的单资源本地事务支持是 JTA 的一种轻量级且强大的替代方案。当您使用本地 EJB 无状态会话 Bean 来驱动事务时，即使您仅访问单个数据库并仅使用无状态会话 Bean 通过容器管理的事务提供声明式事务，您也同时依赖于 EJB 容器和 JTA。直接通过编程方式使用 JTA 也需要 Jakarta EE 环境。

    Spring 驱动的事务可以与本地定义的 Hibernate SessionFactory 配合使用，就像它与本地 JDBC DataSource 配合使用一样，前提是它们访问单个数据库。因此，只有在具有分布式事务需求时，才需要使用 Spring 的 JTA 事务策略。JCA 连接器需要特定于容器的部署步骤，并且（显然）首先需要支持 JCA。此配置比部署带有本地资源定义和 Spring 驱动事务的简单 Web 应用程序需要更多的工作。

    综上所述，如果您不使用 EJB，请坚持使用本地SessionFactory 设置以及 Spring 的HibernateTransactionManager 或JtaTransactionManager。您将获得所有好处，包括适当的 JVM 级事务缓存和分布式事务，而无需容器部署的不便。通过 JCA 连接器注册 HibernateSessionFactory 的 JNDI 仅在结合使用 EJB 时才有价值。

    Hibernate 中的虚假应用服务器警告

    在某些具有非常严格的 XADataSource 实现的 JTA 环境中（目前包括某些 WebLogic Server 和 WebSphere 版本），当 Hibernate 未针对该环境的 JTA 事务管理器进行配置时，应用程序服务器日志中可能会出现虚假的警告或异常。这些警告或异常表明正在访问的连接不再有效或 JDBC 访问不再有效，可能是因为事务已不再处于活动状态。例如，以下是来自 WebLogic 的实际异常：

    java.sql.SQLException: The transaction is no longer active - status: 'Committed'. No
further JDBC access is allowed within this transaction.

    另一个常见问题是 JTA 事务后的连接泄漏，Hibernate 会话（以及潜在的底层 JDBC 连接）未能正确关闭。

    您可以通过让 Hibernate 感知 JTA 事务管理器（Spring 也会与其同步）来解决此类问题。您有两种选择来实现此目的：

    • 将您的 Spring JtaTransactionManager Bean 传递给 Hibernate 配置。最简单的方法是在您的LocalSessionFactoryBean Bean 的 jtaTransactionManager 属性中引用该 Bean（参见Hibernate 事务设置）。Spring 随后会将相应的 JTA 策略提供给 Hibernate。

    • 您还可以在LocalSessionFactoryBean的"hibernateProperties"中显式配置 Hibernate 的 JTA 相关属性，特别是"hibernate.transaction.coordinator_class"、"hibernate.connection.handling_mode"以及可能的"hibernate.transaction.jta.platform"（有关这些属性的详细信息，请参阅 Hibernate 手册）。

    本节其余部分描述了在有无 Hibernate 感知 JTA PlatformTransactionManager 的情况下发生的事件序列。

    当 Hibernate 未配置任何关于 JTA 事务管理器的感知时，在 JTA 事务提交时会发生以下事件：

    • JTA 事务提交。

    • Spring 的JtaTransactionManager与 JTA 事务同步，因此会通过 JTA 事务管理器的afterCompletion回调被调用。

    • 此外，此同步可能会触发 Spring 向 Hibernate 发起回调，通过 Hibernate 的afterTransactionCompletion回调（用于清除 Hibernate 缓存），随后对 Hibernate Session 显式调用close()，从而导致 Hibernate 尝试close()JDBC 连接。

    • 在某些环境中，此Connection.close()调用会触发警告或错误，因为应用程序服务器不再认为该Connection可用，因为事务已经提交。

    当 Hibernate 配置为了解 JTA 事务管理器时，在 JTA 事务提交时会发生以下事件：

    • JTA 事务已准备好提交。

    • Spring 的JtaTransactionManager与 JTA 事务同步，因此 JTA 事务管理器会通过beforeCompletion回调调用该事务。

    • Spring 知道 Hibernate 本身已与 JTA 事务同步，其行为与之前的场景不同。特别是，它与 Hibernate 的事务资源管理保持一致。

    • JTA 事务提交。

    • Hibernate 与 JTA 事务同步，因此 JTA 事务管理器会通过afterCompletion回调调用该事务，从而能够正确清除其缓存。
