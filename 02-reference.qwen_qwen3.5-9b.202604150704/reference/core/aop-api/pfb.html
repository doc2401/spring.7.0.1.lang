    使用ProxyFactoryBean创建 AOP 代理

    如果您使用 Spring IoC 容器（即 ApplicationContext 或 BeanFactory）来管理业务对象（您应该这样做！），则应使用 Spring AOP 的某个 FactoryBean 实现。（请记住，工厂 Bean 引入了一层间接性，使其能够创建不同类型的对象。）

    Spring AOP 支持在底层也使用工厂 Bean。

    在 Spring 中创建 AOP 代理的基本方法是使用 org.springframework.aop.framework.ProxyFactoryBean。这提供了对切点、所有适用的通知及其顺序的完全控制。但是，如果您不需要这种控制，则存在更简单的选项可供选择。

    Basics

    ProxyFactoryBean 与其他 Spring FactoryBean 实现一样，引入了一层间接性。如果您定义了一个名为 foo 的 ProxyFactoryBean，引用 foo 的对象看到的不是 ProxyFactoryBean 实例本身，而是由 ProxyFactoryBean 中 getObject() 方法的实现所创建的对象。该方法会创建一个 AOP 代理来包装目标对象。

    使用 ProxyFactoryBean 或其他 IoC 感知类来创建 AOP 代理的最重要优势之一是，通知（advice）和切入点（pointcuts）也可以由 IoC 进行管理。这是一个强大的功能，使得某些在其他 AOP 框架中难以实现的方法成为可能。例如，一个通知本身可以引用应用程序对象（除了目标对象，任何 AOP 框架都应提供），从而受益于依赖注入所提供的所有可插拔性。

    JavaBean 属性

    与 Spring 提供的大多数 FactoryBean 实现一样，ProxyFactoryBean 类本身也是一个 JavaBean。其属性用于：

    • 指定要代理的目标。

    • 指定是否使用 CGLIB（稍后描述，另见基于 JDK 和 CGLIB 的代理）。

    某些关键属性继承自org.springframework.aop.framework.ProxyConfig(Spring 中所有 AOP 代理工厂的父类)。这些关键属性包括以下内容：

    • proxyTargetClass: 如果要对目标类进行代理，而不是对目标类的接口进行代理，则设置为 true。如果将此属性值设置为 true，则会创建 CGLIB 代理（但也请参阅基于 JDK 和 CGLIB 的代理）。

    • optimize：控制是否对通过 CGLIB 创建的代理应用激进的优化。除非您完全了解相关的 AOP 代理如何处理优化，否则不应随意使用此设置。当前仅用于 CGLIB 代理；对 JDK 动态代理无效。

    • frozen：如果代理配置被设为 frozen，则不再允许对该配置进行修改。这既可作为轻微的优化手段，也可用于防止在创建代理后调用者通过 Advised 接口操纵代理的情况。该属性的默认值为 false，因此允许进行更改（例如添加额外的建议）。

    • exposeProxy：确定是否应将当前代理暴露到ThreadLocal中，以便目标对象可以访问它。如果目标需要获取代理且exposeProxy属性设置为true，则目标可以使用AopContext.currentProxy()方法。

    ProxyFactoryBean 特有的其他属性包括以下内容：

    • proxyInterfaces：一个 String 接口名称数组。如果未提供此项，则为目标类使用 CGLIB 代理（但请参见基于 JDK 和 CGLIB 的代理）。

    • interceptorNames：要应用的 Advisor、拦截器或其他建议名称的 String 数组。顺序很重要，遵循先到先得的原则。也就是说，列表中的第一个拦截器是第一个能够拦截调用的拦截器。

      这些名称是当前工厂中的 Bean 名称，包括来自祖先工厂的 Bean 名称。您不能在此处提及 Bean 引用，因为这样做会导致 ProxyFactoryBean 忽略建议的单例设置。

      您可以使用星号 (*) 附加拦截器名称。这样做会导致所有以星号前部分开头的顾问 bean 被应用。您可以在使用“全局”顾问中找到此功能的示例。

    • singleton：无论调用多少次 getObject() 方法，工厂是否应返回单个对象。几个 FactoryBean 实现提供了此类方法。默认值为 true。如果您想使用有状态的建议（例如，用于有状态的混入），请使用原型建议配合 singleton 值为 false。

    基于 JDK 和 CGLIB 的代理

    本节提供了关于ProxyFactoryBean如何为特定目标对象（即需要代理的对象）选择创建基于 JDK 的代理还是基于 CGLIB 的代理的权威文档。

    在 Spring 1.2.x 和 2.0 版本之间，ProxyFactoryBean 创建基于 JDK 或 CGLIB 的代理的行为发生了变化。ProxyFactoryBean 现在在自动检测接口方面表现出与 TransactionProxyFactoryBean 类相似的语义。

    如果待代理的目标对象（以下简称目标类）的类未实现任何接口，则创建基于 CGLIB 的代理。这是最简单的情况，因为 JDK 代理是基于接口的，没有接口就意味着无法使用 JDK 代理。您可以通过设置 interceptorNames 属性来插入目标 Bean 并指定拦截器列表。请注意，即使已将 ProxyFactoryBean 的 proxyTargetClass 属性设置为 false，也会创建基于 CGLIB 的代理。（这样做毫无意义，最好从 Bean 定义中移除它，因为至多只是冗余，最坏则令人困惑。）

    如果目标类实现了一个（或多个）接口，则创建的代理类型取决于ProxyFactoryBean的配置。

    如果ProxyFactoryBean的proxyTargetClass属性已设置为true，则创建基于CGLIB的代理。这是合理的，也符合“最少惊讶原则”。即使ProxyFactoryBean的proxyInterfaces属性已设置为一个或多个完全限定的接口名称，只要proxyTargetClass属性设置为true，基于CGLIB的代理机制就会生效。

    如果ProxyFactoryBean的proxyInterfaces属性已设置为一个或多个完全限定的接口名称，则将创建基于 JDK 的代理。创建的代理实现了在proxyInterfaces属性中指定的所有接口。如果目标类恰好实现了比proxyInterfaces属性中指定的那些多得多的接口，那也无妨，但这些额外的接口不会被返回的代理实现。

    如果未设置 ProxyFactoryBean 的 proxyInterfaces 属性，但目标类实现了（一个或多个）接口，ProxyFactoryBean 会自动检测到目标类确实实现了至少一个接口，并创建基于 JDK 的代理。实际被代理的接口是目标类实现的所有接口。实际上，这与向 proxyInterfaces 属性提供目标类实现的每个接口的列表效果相同。然而，这样做工作量显著更小，且不易出现拼写错误。

    代理接口

    考虑一下 ProxyFactoryBean 的一个简单示例。该示例涉及以下内容：

    • 一个被代理的目标 Bean。这是示例中的personTargetBean 定义。

    • Advisor 和 Interceptor 用于提供建议。

    • 用于指定目标对象（即personTarget 豆）、要代理的接口以及要应用的建议的 AOP 代理豆定义。

    以下列表显示了示例：

    <bean id="personTarget" class="com.mycompany.PersonImpl">
	<property name="name" value="Tony"/>
	<property name="age" value="51"/>
</bean>

<bean id="myAdvisor" class="com.mycompany.MyAdvisor">
	<property name="someProperty" value="Custom string property value"/>
</bean>

<bean id="debugInterceptor" class="org.springframework.aop.interceptor.DebugInterceptor">
</bean>

<bean id="person"
	class="org.springframework.aop.framework.ProxyFactoryBean">
	<property name="proxyInterfaces" value="com.mycompany.Person"/>

	<property name="target" ref="personTarget"/>
	<property name="interceptorNames">
		<list>
			<value>myAdvisor</value>
			<value>debugInterceptor</value>
		</list>
	</property>
</bean>

    注意，interceptorNames 属性接受一个 String 列表，其中包含当前工厂中拦截器或顾问的 bean 名称。您可以使用顾问、拦截器以及 before、after、returning 和 throws 通知对象。顾问的顺序非常重要。

    您可能想知道为什么列表不持有 bean 引用。原因是，如果将 ProxyFactoryBean 的 singleton 属性设置为 false，则必须能够返回独立的代理实例。如果任何 advisor 本身是 prototype，则需要返回一个独立实例，因此必须能够从工厂获取该 prototype 的实例。仅持有引用是不够的。

    之前显示的 person Bean 定义可用于替代 Person 实现，如下所示：

    • Java

    • Kotlin

    Person person = (Person) factory.getBean("person");
    val person = factory.getBean("person") as Person

    同一 IoC 上下文中的其他 Bean 可以像普通 Java 对象一样，对其表达强类型依赖。以下示例展示了如何做到这一点：

    <bean id="personUser" class="com.mycompany.PersonUser">
	<property name="person"><ref bean="person"/></property>
</bean>

    此示例中的 PersonUser 类暴露了一个类型为 Person 的属性。就其而言，AOP 代理可以透明地替代“真实”的 Person 实现。然而，该类将是一个动态代理类。可以将它转换为 Advised 接口（稍后讨论）。

    您可以通过使用匿名内部 Bean 来隐藏目标对象和代理之间的区别。只有ProxyFactoryBean的定义有所不同。建议仅包含以作完整说明。以下示例展示了如何使用匿名内部 Bean：

    <bean id="myAdvisor" class="com.mycompany.MyAdvisor">
	<property name="someProperty" value="Custom string property value"/>
</bean>

<bean id="debugInterceptor" class="org.springframework.aop.interceptor.DebugInterceptor"/>

<bean id="person" class="org.springframework.aop.framework.ProxyFactoryBean">
	<property name="proxyInterfaces" value="com.mycompany.Person"/>
	<!-- Use inner bean, not local reference to target -->
	<property name="target">
		<bean class="com.mycompany.PersonImpl">
			<property name="name" value="Tony"/>
			<property name="age" value="51"/>
		</bean>
	</property>
	<property name="interceptorNames">
		<list>
			<value>myAdvisor</value>
			<value>debugInterceptor</value>
		</list>
	</property>
</bean>

    使用匿名内部 Bean 的优势在于只有一个 Person 类型的对象。如果我们要防止应用程序上下文的用户获取未代理对象的引用，或者需要避免与 Spring IoC 自动装配产生歧义，这非常有用。此外，ProxyFactoryBean 的定义是自包含的，这也算是一个优势。然而，在某些情况下（例如某些测试场景），能够从工厂中获取未代理的目标对象可能实际上是一个优势。

    代理类

    那如果您需要代理一个类，而不是一个或多个接口呢？

    假设在我们之前的示例中，没有 Person 接口。我们需要对名为 Person 的类进行增强，而该类并未实现任何业务接口。在这种情况下，您可以配置 Spring 使用 CGLIB 代理而非动态代理。为此，请将前面所示的 ProxyFactoryBean 上的 proxyTargetClass 属性设置为 true。虽然编程时最好面向接口而非类，但在处理遗留代码时，对未实现接口的类进行增强的能力可能非常有用。（总体而言，Spring 并不强加特定规范。它使应用良好实践变得容易，但避免强制采用某种特定方法。）

    如果您愿意，可以强制在任何情况下使用 CGLIB，即使您确实拥有接口。

    CGLIB 代理通过在运行时生成目标类的子类来工作。Spring 配置该生成的子类，将方法调用委托给原始目标。该子类用于实现装饰器模式，并织入通知（advice）。

    CGLIB 代理通常对用户是透明的。然而，有一些问题需要考虑：

    • final 类无法被代理，因为它们不能被扩展。

    • final 方法无法进行增强，因为它们不能被重写。

    • private 方法无法进行增强，因为它们不能被重写。

    • 无法对不可见的方法（通常是来自不同包中的父类的包私有方法）进行增强，因为它们实际上等同于私有方法。

    无需将 CGLIB 添加到类路径中。CGLIB 已重新打包并包含在 spring-core JAR 中。换句话说，基于 CGLIB 的 AOP 和 JDK 动态代理都可以“开箱即用”。

    CGLIB 代理和动态代理之间的性能差异很小。在这种情况下，性能不应作为决定性因素。

    Using “Global” Advisors

    通过在拦截器名称后添加星号，所有 bean 名称与星号前部分匹配的 Advisor 将被添加到 Advisor 链中。如果您需要添加一组标准的“全局”Advisor，这可能会派上用场。以下示例定义了两个全局 Advisor：

    <bean id="proxy" class="org.springframework.aop.framework.ProxyFactoryBean">
	<property name="target" ref="service"/>
	<property name="interceptorNames">
		<list>
			<value>global*</value>
		</list>
	</property>
</bean>

<bean id="global_debug" class="org.springframework.aop.interceptor.DebugInterceptor"/>
<bean id="global_performance" class="org.springframework.aop.interceptor.PerformanceMonitorInterceptor"/>
