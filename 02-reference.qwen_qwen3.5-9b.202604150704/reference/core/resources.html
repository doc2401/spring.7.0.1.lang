    Introduction

    Java 标准的 java.net.URL 类以及用于各种 URL 前缀的标准处理器，不幸的是，对于访问底层资源而言尚不够完善。例如，没有标准化的 URL 实现可用于从类路径获取资源或相对于 ServletContext 获取资源。虽然可以为专用的 URL 前缀注册新处理器（类似于现有的 http: 等前缀的处理器），但这通常相当复杂，而且 URL 接口仍缺少一些理想的功能，例如检查所指向资源是否存在的方法。

    The Resource Interface

    Spring 位于 org.springframework.core.io. 包中的 Resource 接口旨在提供一个功能更强大的接口，用于抽象对底层资源的访问。以下列表概述了 Resource 接口。有关更多详细信息，请参阅 Resource javadoc。

    public interface Resource extends InputStreamSource {

	boolean exists();

	boolean isReadable();

	boolean isOpen();

	boolean isFile();

	URL getURL() throws IOException;

	URI getURI() throws IOException;

	File getFile() throws IOException;

	ReadableByteChannel readableChannel() throws IOException;

	long contentLength() throws IOException;

	long lastModified() throws IOException;

	Resource createRelative(String relativePath) throws IOException;

	String getFilename();

	String getDescription();
}

    正如Resource接口的定义所示，它扩展了InputStreamSource接口。以下列出的是InputStreamSource接口的定义：

    public interface InputStreamSource {

	InputStream getInputStream() throws IOException;
}

    Resource 接口的一些最重要的方法是：

    • getInputStream()：定位并打开资源，返回一个 InputStream 用于从该资源读取数据。预期每次调用都会返回一个新的 InputStream。关闭流的责任由调用者承担。

    • exists()：返回一个 boolean，指示此资源在物理形式上是否实际存在。

    • isOpen()：返回一个 boolean，指示此资源是否表示具有打开流句柄。如果为 true，则 InputStream 不能多次读取，必须仅读取一次然后关闭以避免资源泄漏。对于所有常规资源实现均返回 false，InputStreamResource 除外。

    • getDescription()：返回此资源的描述，用于在与该资源交互时的错误输出。这通常是资源的完全限定文件名或实际 URL。

    其他方法允许您获取代表该资源的实际URL或File对象（如果底层实现兼容并支持此功能）。

    某些 Resource 接口的实现也实现了扩展的WritableResource接口，以支持向资源写入数据。

    Spring 本身广泛使用Resource抽象，在许多需要资源的方法签名中作为参数类型。某些 Spring API 中的其他方法（例如各种ApplicationContext实现的构造函数）接受一个String，该字符串以未修饰或简单形式用于创建适合该上下文实现的Resource；或者通过String路径上的特殊前缀，让调用者指定必须创建并使用特定的Resource实现。

    虽然 `Resource` 接口被 Spring 广泛使用，但它实际上作为一个通用工具类在您的代码中单独使用时也非常方便，可用于访问资源，即使您的代码并不了解或关心 Spring 的其他部分。虽然这会将您的代码与 Spring 耦合，但它实际上仅将其与该小集工具类耦合，这些类可作为功能更强大的 `URL` 替代品，可被视为用于此目的的任何其他库的等效物。

    Resource 抽象并不替代功能，而是在可能的情况下对其进行封装。例如，UrlResource 封装一个 URL，并使用封装的 URL 来执行其工作。

    Built-in Resource Implementations

    Spring 包含几个内置的Resource实现：

    • UrlResource

    • ClassPathResource

    • FileSystemResource

    • PathResource

    • ServletContextResource

    • InputStreamResource

    • ByteArrayResource

    要获取 Spring 中可用的 Resource 实现的完整列表，请查阅 Resource javadoc 中的“所有已知实现类”部分。

    UrlResource

    UrlResource 封装了一个 java.net.URL，可用于访问通常通过 URL 可访问的任何对象，例如文件、HTTPS 目标、FTP 目标以及其他资源。所有 URL 都具有标准化的 String 表示形式，从而使用适当的标准化前缀来区分不同的 URL 类型。这包括用于访问文件系统路径的 file:、用于通过 HTTPS 协议访问资源的 https:、用于通过 FTP 访问资源的 ftp: 以及其他类型。

    UrlResource 是由 Java 代码通过显式使用 UrlResource 构造函数创建的，但通常在调用接受代表路径的 String 参数的 API 方法时隐式创建。在后一种情况下，JavaBeans PropertyEditor 最终决定创建哪种类型的 Resource。如果路径字符串包含属性编辑器熟知的（即）前缀（例如 classpath:），它将为此前缀创建适当的专用 Resource。但是，如果它无法识别该前缀，则假定该字符串是标准 URL 字符串，并创建一个 UrlResource。

    ClassPathResource

    该类表示应从类路径中获取的资源。它使用线程上下文类加载器、给定的类加载器或给定的类来加载资源。

    此Resource实现支持将类路径资源解析为java.io.File，前提是该类路径资源位于文件系统中；但对于驻留在 jar 中且尚未被 servlet 引擎或环境展开到文件系统的类路径资源则不支持。为解决这一问题，各种Resource实现始终支持将其解析为java.net.URL。

    `ClassPathResource` 是由 Java 代码通过显式使用 `ClassPathResource` 构造函数创建的，但通常在调用接受表示路径的 `String` 参数的 API 方法时隐式创建。在后一种情况下，JavaBeans `PropertyEditor` 会识别字符串路径上的特殊前缀 `classpath:`，并在此情况下创建一个 `ClassPathResource`。

    FileSystemResource

    这是针对`java.io.File`句柄的Resource实现。它还支持java.nio.file.Path句柄，应用 Spring 的标准基于字符串的路径转换，但通过java.nio.file.Files API 执行所有操作。对于纯java.nio.path.Path支持，请使用PathResource。FileSystemResource支持解析为File和URL。

    PathResource

    这是一个针对 `java.nio.file.Path` 句柄的 `Resource` 实现，通过 `Path API 执行所有操作和转换。它支持解析为 `File` 和 `URL`，并实现了扩展的 `WritableResource` 接口。PathResource 本质上是基于纯 `java.nio.path.Path` 的 `FileSystemResource` 替代方案，具有不同的 `createRelative` 行为。

    ServletContextResource

    这是一个针对 `ServletContext` 资源的 `Resource` 实现，它会在相关 Web 应用的根目录内解析相对路径。

    它始终支持流访问和 URL 访问，但仅当 Web 应用程序归档已展开且资源物理位于文件系统时，才允许 java.io.File 访问。无论其是否已展开并位于文件系统，还是直接从 JAR 或其他位置（如数据库，这是可以想象的）直接访问，这实际上取决于 Servlet 容器。

    InputStreamResource

    InputStreamResource 是针对给定 InputStream 的 Resource 实现。仅在没有任何特定的 Resource 实现适用时才应使用它。特别是，在可能的情况下，请优先使用 ByteArrayResource 或任何基于文件的 Resource 实现。

    与其他Resource实现不同，这是一个已打开资源的描述符。因此，它从isOpen()返回true。如果您需要保留资源描述符或需要多次读取流，请勿使用它。

    ByteArrayResource

    这是一个针对给定字节数组的 Resource 实现。它会为给定的字节数组创建一个 ByteArrayInputStream。

    它可用于从任意给定的字节数组加载内容，而无需使用一次性的InputStreamResource。

    The ResourceLoader Interface

    ResourceLoader 接口旨在由能够返回（即加载）Resource 实例的对象实现。以下列表展示了 ResourceLoader 接口的定义：

    public interface ResourceLoader {

	Resource getResource(String location);

	ClassLoader getClassLoader();
}

    所有应用上下文都实现了ResourceLoader接口。因此，所有应用上下文都可以用于获取Resource实例。

    当您在特定的应用上下文中调用getResource()，且指定的位置路径没有特定前缀时，您将获得一个适用于该特定应用上下文的Resource 类型。例如，假设以下代码片段是在一个ClassPathXmlApplicationContext 实例上运行的：

    • Java

    • Kotlin

    Resource template = ctx.getResource("some/resource/path/myTemplate.txt");
    val template = ctx.getResource("some/resource/path/myTemplate.txt")

    对于 `ClassPathXmlApplicationContext`，该代码返回一个 `ClassPathResource`。如果将相同的方法运行在 `FileSystemXmlApplicationContext` 实例上，它将返回一个 `FileSystemResource`。对于 `WebApplicationContext`，它将返回一个 `ServletContextResource`。它也会为每个上下文返回相应的对象。

    因此，您可以根据特定的应用程序上下文以适当的方式加载资源。

    另一方面，您可以通过指定特殊的 classpath: 前缀来强制使用 ClassPathResource，无论应用程序上下文类型如何，如下例所示：

    • Java

    • Kotlin

    Resource template = ctx.getResource("classpath:some/resource/path/myTemplate.txt");
    val template = ctx.getResource("classpath:some/resource/path/myTemplate.txt")

    同样，您可以通过指定任何标准 java.net.URL 前缀来强制使用 UrlResource。以下示例使用了 file 和 https 前缀：

    • Java

    • Kotlin

    Resource template = ctx.getResource("file:///some/resource/path/myTemplate.txt");
    val template = ctx.getResource("file:///some/resource/path/myTemplate.txt")

    • Java

    • Kotlin

    Resource template = ctx.getResource("https://myhost.com/resource/path/myTemplate.txt");
    val template = ctx.getResource("https://myhost.com/resource/path/myTemplate.txt")

    下表总结了将String对象转换为Resource对象的策略：

    表 1. 资源字符串
    Prefix Example Explanation

    classpath:

    classpath:com/myapp/config.xml

    从类路径加载。

    file:

    file:///data/config.xml

    作为文件系统上的URL加载。另见FileSystemResource 注意事项。

    https:

    https://myserver/logo.png

    作为URL加载。

    (none)

    /data/config.xml

    取决于底层的ApplicationContext。

    The ResourcePatternResolver Interface

    ResourcePatternResolver 接口是 ResourceLoader 接口的扩展，它定义了一种策略，用于将位置模式（例如 Ant 风格的路径模式）解析为 Resource 对象。

    public interface ResourcePatternResolver extends ResourceLoader {

	String CLASSPATH_ALL_URL_PREFIX = "classpath*:";

	Resource[] getResources(String locationPattern) throws IOException;
}

    如上所示，该接口还为类路径中所有匹配的资源定义了一个特殊的 classpath*: 资源前缀。请注意，在这种情况下，资源位置预期是一个不包含占位符的路径——例如，classpath*:/config/beans.xml。类路径中的 JAR 文件或不同目录可以包含多个具有相同路径和名称的文件。有关使用 classpath*: 资源前缀的通配符支持，请参阅应用程序上下文构造函数资源路径中的通配符及其子部分以获取详细信息。

    传入的ResourceLoader（例如，通过ResourceLoaderAware语义提供的）可以检查它是否也实现了这个扩展接口。

    `PathMatchingResourcePatternResolver` 是一个独立的实现，可以在 `ApplicationContext` 之外使用，同时也由 `ResourceArrayPropertyEditor` 用于填充 `Resource[]` Bean 属性。`PathMatchingResourcePatternResolver` 能够将指定的资源位置路径解析为一个或多个匹配的 `Resource` 对象。源路径可以是一个与目标 `Resource` 具有一对一映射的简单路径，或者包含特殊前缀 `classpath*:` 和/或内部 Ant 风格正则表达式（使用 Spring 的 `org.springframework.util.AntPathMatcher` 工具进行匹配）。后两者本质上都是通配符。

    标准 ApplicationContext 中的默认 ResourceLoader 实际上是 PathMatchingResourcePatternResolver 的一个实例，该实例实现了 ResourcePatternResolver 接口。对于 ApplicationContext 实例本身也是如此，它也实现了 ResourcePatternResolver 接口并委托给默认的 PathMatchingResourcePatternResolver。

    The ResourceLoaderAware Interface

    ResourceLoaderAware 接口是一个特殊的回调接口，用于标识期望获得 ResourceLoader 引用的组件。以下列表展示了 ResourceLoaderAware 接口的定义：

    public interface ResourceLoaderAware {

	void setResourceLoader(ResourceLoader resourceLoader);
}

    当某个类实现了ResourceLoaderAware接口并被部署到应用上下文中（作为 Spring 管理的 Bean）时，该应用上下文会将其识别为ResourceLoaderAware。随后，应用上下文将调用setResourceLoader(ResourceLoader)方法，并将自身作为参数传入（请记住，Spring 中的所有应用上下文都实现了ResourceLoader接口）。

    由于 ApplicationContext 是一个 ResourceLoader，该 Bean 也可以实现 ApplicationContextAware 接口并直接使用提供的 ApplicationContext 加载资源。然而，通常情况下，如果仅需此功能，最好使用专门的 ResourceLoader 接口。这样代码将仅耦合到资源加载接口（可视为一个工具接口），而不会耦合到整个 Spring ApplicationContext 接口。

    在应用程序组件中，您也可以依赖对 ResourceLoader 的自动装配，作为实现 ResourceLoaderAware 接口的替代方案。传统 的 constructor 和 byType 自动装配模式（如Autowiring Collaborators中所述）能够为构造函数参数或 setter 方法参数分别提供 ResourceLoader。为了获得更大的灵活性（包括能够自动装配字段和多个参数的方法），请考虑使用基于注解的自动装配功能。在这种情况下，只要相关的字段、构造函数或方法带有 @Autowired 注解，ResourceLoader 就会被自动装配到期望 ResourceLoader 类型的字段、构造函数参数或方法参数中。有关更多信息，请参阅使用 @Autowired。

    若要加载包含通配符的资源路径或使用了特殊 classpath*: 资源前缀的一个或多个 Resource 对象，建议将 ResourcePatternResolver 的实例自动注入到应用程序组件中，而不是使用 ResourceLoader。

    资源作为依赖项

    如果 Bean 本身将通过某种动态过程确定并提供资源路径，那么让 Bean 使用ResourceLoader或ResourcePatternResolver接口来加载资源可能是合理的。例如，考虑加载某种模板的情况，其中所需的特定资源取决于用户的角色。如果资源是静态的，则完全消除对ResourceLoader接口（或ResourcePatternResolver接口）的使用是有意义的，让 Bean 暴露其需要的Resource属性，并期望它们被注入到该 Bean 中。

    使其变得轻而易举地注入这些属性的是，所有应用上下文都注册并使用特殊的 JavaBeans PropertyEditor，该编辑器可以将 String 路径转换为 Resource 对象。例如，以下 MyBean 类具有类型为 Resource 的 template 属性。

    • Java

    • Kotlin

    public class MyBean {

	private Resource template;

	public setTemplate(Resource template) {
		this.template = template;
	}

	// ...
}
    class MyBean(var template: Resource)

    在 XML 配置文件中，template 属性可以使用简单的字符串来配置该资源，如下例所示：

    <bean id="myBean" class="example.MyBean">
	<property name="template" value="some/resource/path/myTemplate.txt"/>
</bean>

    请注意，资源路径没有前缀。因此，由于应用程序上下文本身将被用作 ResourceLoader，资源将通过 ClassPathResource、FileSystemResource 或 ServletContextResource 加载，具体取决于应用程序上下文的实际类型。

    如果需要强制使用特定的Resource类型，可以使用前缀。以下两个示例展示了如何强制使用ClassPathResource和UrlResource（后者用于访问文件系统中的文件）：

    <property name="template" value="classpath:some/resource/path/myTemplate.txt">
    <property name="template" value="file:///some/resource/path/myTemplate.txt"/>

    如果将MyBean类重构为使用注解驱动的配置，可以将myTemplate.txt的路径存储在一个名为template.path的键下——例如，在提供给 Spring Environment的属性文件中（参见环境抽象）。然后可以通过@Value注解使用属性占位符引用模板路径（参见使用@Value）。Spring 将检索模板路径的值作为字符串，一个特殊的PropertyEditor会将该字符串转换为Resource对象并注入到MyBean的构造函数中。以下示例演示了如何实现此操作。

    • Java

    • Kotlin

    @Component
public class MyBean {

	private final Resource template;

	public MyBean(@Value("${template.path}") Resource template) {
		this.template = template;
	}

	// ...
}
    @Component
class MyBean(@Value("\${template.path}") private val template: Resource)

    如果我们要支持在类路径的多个位置（例如，类路径中的多个 jar 文件）发现同一路径下的多个模板，我们可以使用特殊的 classpath*: 前缀和通配符来定义 templates.path 键为 classpath*:/config/templates/*.txt。如果我们按如下方式重新定义 MyBean 类，Spring 会将模板路径模式转换为 Resource 对象数组，并将其注入到 MyBean 的构造函数中。

    • Java

    • Kotlin

    @Component
public class MyBean {

	private final Resource[] templates;

	public MyBean(@Value("${templates.path}") Resource[] templates) {
		this.templates = templates;
	}

	// ...
}
    @Component
class MyBean(@Value("\${templates.path}") private val templates: Resource[])

    应用上下文和资源路径

    本节介绍如何使用资源创建应用程序上下文，包括适用于 XML 的快捷方式、通配符的使用以及其他详细信息。

    构建应用上下文

    应用程序上下文构造函数（针对特定类型的应用程序上下文）通常接受字符串或字符串数组作为资源的位置路径，例如构成上下文定义的 XML 文件。

    当此类位置路径没有前缀时，由该路径构建并用于加载 Bean 定义的特定 Resource 类型取决于具体的应用程序上下文，并且适用于该上下文。例如，考虑以下示例，它创建了一个 ClassPathXmlApplicationContext：

    • Java

    • Kotlin

    ApplicationContext ctx = new ClassPathXmlApplicationContext("conf/appContext.xml");
    val ctx = ClassPathXmlApplicationContext("conf/appContext.xml")

    bean 定义是从类路径中加载的，因为使用了 ClassPathResource。然而，请考虑以下示例，该示例创建了一个 FileSystemXmlApplicationContext：

    • Java

    • Kotlin

    ApplicationContext ctx =
	new FileSystemXmlApplicationContext("conf/appContext.xml");
    val ctx = FileSystemXmlApplicationContext("conf/appContext.xml")

    现在，bean 定义已从文件系统位置加载（在本例中，相对于当前工作目录）。

    请注意，在位置路径中使用特殊classpath前缀或标准 URL 前缀会覆盖用于加载 Bean 定义的默认Resource类型。考虑以下示例：

    • Java

    • Kotlin

    ApplicationContext ctx =
	new FileSystemXmlApplicationContext("classpath:conf/appContext.xml");
    val ctx = FileSystemXmlApplicationContext("classpath:conf/appContext.xml")

    使用 FileSystemXmlApplicationContext 会从类路径中加载 bean 定义。然而，它仍然是一个 FileSystemXmlApplicationContext。如果随后将其用作 ResourceLoader，任何未加前缀的路径仍被视为文件系统路径。

    Constructing ClassPathXmlApplicationContext Instances — Shortcuts

    ClassPathXmlApplicationContext 提供了多个构造函数以方便实例化。其基本思想是，您只需提供一个仅包含 XML 文件名（不含前导路径信息）的字符串数组，并提供一个 Class。ClassPathXmlApplicationContext 将从提供的类中推导出路径信息。

    考虑以下目录结构：

    com/
  example/
    services.xml
    repositories.xml
    MessengerService.class

    下面的示例展示了如何实例化一个由类路径中名为services.xml和repositories.xml（位于类路径下）的文件中定义的 bean 组成的ClassPathXmlApplicationContext实例：

    • Java

    • Kotlin

    ApplicationContext ctx = new ClassPathXmlApplicationContext(
	new String[] {"services.xml", "repositories.xml"}, MessengerService.class);
    val ctx = ClassPathXmlApplicationContext(arrayOf("services.xml", "repositories.xml"), MessengerService::class.java)

    有关各种构造函数的详细信息，请参阅 ClassPathXmlApplicationContext javadoc。

    应用程序上下文构造函数资源路径中的通配符

    应用程序上下文构造函数值中的资源路径可以是简单路径（如前所示），每个路径与目标 Resource 具有一对一映射关系；或者，它们可以包含特殊前缀 classpath*: 或内部 Ant 风格模式（通过 Spring 的 PathMatcher 工具进行匹配）。后两者实际上都是通配符。

    该机制的一个用途是进行组件式应用程序组装。所有组件都可以将上下文定义片段发布到已知的路径位置，并且当使用带有 classpath*: 前缀的相同路径创建最终的应用程序上下文时，会自动拾取所有组件片段。

    请注意，这种通配符用法仅适用于应用程序上下文构造函数中的资源路径（或直接使用PathMatcher工具类层次结构时），并在构造时解析。它与Resource类型本身无关。您不能使用classpath*:前缀来构建实际的Resource，因为一个资源一次仅指向一个资源。

    Ant 风格模式

    路径位置可以包含 Ant 风格模式，如下例所示：

    /WEB-INF/*-context.xml
com/mycompany/**/applicationContext.xml
file:C:/some/path/*-context.xml
classpath:com/mycompany/**/applicationContext.xml

    当路径位置包含 Ant 风格模式时，解析器会遵循更复杂的流程以尝试解析通配符。它会为直到最后一个非通配符段的路径生成一个 Resource 并从中获取 URL。如果该 URL 不是 jar: URL 或容器特定变体（例如 WebLogic 中的 zip:、WebSphere 中的 wsjar 等），则会从中获取一个 java.io.File 并通过遍历文件系统来解析通配符。对于 jar URL，解析器会从中获取一个 java.net.JarURLConnection 或手动解析该 jar URL，然后遍历 jar 文件的内容以解析通配符。

    对可移植性的影响

    如果指定的路径已经是 `file` 协议（无论是隐式地因为基础 `ResourceLoader 是文件系统加载器，还是显式指定），则通配符匹配保证能以完全可移植的方式工作。

    如果指定的路径是 classpath 位置，解析器必须通过调用 Classloader.getResource() 获取最后一个非通配符路径段 URL。由于这仅仅是路径中的一个节点（而非末尾的文件），在 ClassLoader 的 JavaDoc 中，实际上并未明确定义在这种情况下返回何种类型的 URL。在实践中，它始终是一个代表目录的 java.io.File（其中 classpath 资源解析为文件系统位置）或某种形式的 jar URL（其中 classpath 资源解析为 jar 位置）。尽管如此，此操作仍存在可移植性问题。

    如果为最后一个非通配符段获取了 jar URL，解析器必须能够从该 URL 获取一个 java.net.JarURLConnection 或手动解析该 jar URL，以便遍历 jar 的内容并解析通配符。这在大多数环境中可以正常工作，但在其他环境中会失败，因此我们强烈建议您在依赖它之前，在特定环境中彻底测试来自 jar 的资源通配符解析功能。

    The classpath*: Prefix

    在构建基于 XML 的应用程序上下文时，位置字符串可以使用特殊前缀classpath*:，如下例所示：

    • Java

    • Kotlin

    ApplicationContext ctx =
	new ClassPathXmlApplicationContext("classpath*:conf/appContext.xml");
    val ctx = ClassPathXmlApplicationContext("classpath*:conf/appContext.xml")

    此特殊前缀指定必须获取所有匹配给定名称的类路径资源（内部，这本质上是通过调用 ClassLoader.getResources(…​) 实现的），然后将它们合并以形成最终的应用程序上下文定义。

    通配符类路径依赖于底层 ClassLoader 的 getResources() 方法。由于如今大多数应用服务器都提供自己的 ClassLoader 实现，其行为可能会有所不同，尤其是在处理 jar 文件时。一个简单的测试方法是检查 classpath* 是否有效：使用 ClassLoader 从类路径中的 jar 内加载一个文件：getClass().getClassLoader().getResources("<someFileInsideTheJar>")。请尝试此测试，使用名称相同但位于两个不同位置的文件——例如，在类路径中不同 jar 中具有相同名称和相同路径的文件。如果返回了不适当的结果，请查阅应用服务器文档，查找可能影响 ClassLoader 行为的设置。

    您还可以在位置路径的其余部分将 classpath*: 前缀与 PathMatcher 模式结合使用（例如，classpath*:META-INF/*-beans.xml）。在这种情况下，解析策略相当简单：对最后一个非通配符路径段调用 ClassLoader.getResources() 以获取类加载器层次结构中的所有匹配资源，然后针对每个资源，对通配符子路径使用前面描述的相同 PathMatcher 解析策略。

    与通配符相关的其他说明

    请注意，当 classpath*: 与 Ant 风格模式结合使用时，除非实际目标文件位于文件系统中，否则只有在模式开始之前至少有一个根目录的情况下才能可靠工作。这意味着像 classpath*:*.xml 这样的模式可能无法从 jar 文件的根目录检索文件，而只能从已展开目录的根目录检索文件。

    Spring 获取类路径条目的能力源自 JDK 的ClassLoader.getResources()方法，该方法仅对空字符串返回文件系统位置（表示潜在的搜索根）。Spring 还会评估URLClassLoader运行时配置以及 jar 文件中的java.class.path清单，但这并不能保证可移植的行为。

    类路径包的扫描需要在类路径中存在相应的目录条目。使用 Ant 构建 JAR 时，请勿激活 JAR 任务的 files-only 开关。此外，在某些环境中，类路径目录可能无法根据安全策略暴露——例如，在 JDK 1.7.0_45 及更高版本上运行的独立应用程序（需要在清单中设置 'Trusted-Library'）。请参阅 stackoverflow.com/questions/19394570/java-jre-7u45-breaks-classloader-getresources。

    在模块路径（Java 模块系统）上，Spring 的类路径扫描通常能按预期工作。在此处也将资源放入专用目录是高度推荐的，这样可以避免上述搜索 jar 文件根目录时出现的可移植性问题。

    使用 classpath: 资源的 Ant 风格模式，如果根包在多个类路径位置中可用，则不能保证找到匹配的资源。考虑以下资源位置的示例：

    com/mycompany/package1/service-context.xml

    现在考虑某人可能用来尝试查找该文件的 Ant 风格路径：

    classpath:com/mycompany/**/service-context.xml

    此类资源在类路径中可能仅存在于一个位置，但在使用如前例所示的路径尝试解析它时，解析器会基于 `getResource("com/mycompany");` 返回的（第一个）URL 进行操作。如果该基础包节点存在于多个 `ClassLoader` 位置中，则目标资源可能并不存在于找到的第一个位置。因此，在这种情况下，您应优先使用带有相同 Ant 风格模式的 `classpath*:`，以搜索包含 `com.mycompany` 基础包的所有类路径位置：classpath*:com/mycompany/**/service-context.xml。

    FileSystemResource Caveats

    未附加到 FileSystemApplicationContext 的 FileSystemResource（即，当 FileSystemApplicationContext 不是实际的 ResourceLoader 时）会按照预期处理绝对路径和相对路径。相对路径相对于当前工作目录，而绝对路径相对于文件系统根目录。

    出于向后兼容性（历史）原因，当FileSystemApplicationContext作为ResourceLoader时，此行为会发生变化。FileSystemApplicationContext强制所有附加的FileSystemResource实例将所有位置路径视为相对路径，无论其是否以斜杠开头。实际上，这意味着以下示例是等效的：

    • Java

    • Kotlin

    ApplicationContext ctx =
	new FileSystemXmlApplicationContext("conf/context.xml");
    val ctx = FileSystemXmlApplicationContext("conf/context.xml")

    • Java

    • Kotlin

    ApplicationContext ctx =
	new FileSystemXmlApplicationContext("/conf/context.xml");
    val ctx = FileSystemXmlApplicationContext("/conf/context.xml")

    以下示例也是等价的（尽管它们本应不同，因为一个是相对路径，另一个是绝对路径）：

    • Java

    • Kotlin

    FileSystemXmlApplicationContext ctx = ...;
ctx.getResource("some/resource/path/myTemplate.txt");
    val ctx: FileSystemXmlApplicationContext = ...
ctx.getResource("some/resource/path/myTemplate.txt")

    • Java

    • Kotlin

    FileSystemXmlApplicationContext ctx = ...;
ctx.getResource("/some/resource/path/myTemplate.txt");
    val ctx: FileSystemXmlApplicationContext = ...
ctx.getResource("/some/resource/path/myTemplate.txt")

ctx.getResource("file:///some/resource/path/myTemplate.txt")
