    Overview

    Spring WebFlux 为何被创建？

    部分原因在于需要一种非阻塞 Web 堆栈，以便用少量线程处理并发，并用更少的硬件资源进行扩展。Servlet 的非阻塞 I/O 使其偏离了 Servlet API 的其余部分，后者包含同步（Filter、Servlet）或阻塞（getParameter、getPart）的契约。这就是创建新通用 API 作为任何非阻塞运行时基础的动机。这一点很重要，因为像 Netty 这样的服务器在异步、非阻塞领域已非常成熟。

    答案的另一部分是函数式编程。正如 Java 5 中注解的引入创造了机会（例如带注解的 REST 控制器或单元测试），Java 8 中 lambda 表达式的引入为 Java 中的函数式 API 创造了机会。这对于非阻塞应用程序和延续风格的 API（如由CompletableFuture和ReactiveX所普及）大有裨益，这些 API 允许以声明方式组合异步逻辑。在编程模型层面，Java 8 使 Spring WebFlux 能够提供功能式 Web 端点，与带注解的控制器并存。

    Define “Reactive”

    我们提到了“非阻塞”和“函数式”，但什么是响应式？

    “响应式”（reactive）一词指的是围绕对变化做出反应而构建的编程模型——例如网络组件对 I/O 事件做出反应，UI 控制器对鼠标事件做出反应等。从这个意义上讲，非阻塞是响应式的，因为我们不再处于阻塞状态，而是进入了一种在操作完成或数据可用时响应通知的模式。

    Spring 团队还将“响应式”与另一个重要机制联系起来，即非阻塞背压。在同步命令式代码中，阻塞调用作为一种自然的背压形式，迫使调用方等待。在非阻塞代码中，控制事件速率变得尤为重要，以防止快速的生产者淹没其目的地。

    Reactive Streams 是一个小型规范（也已在 Java 9 中采纳），它定义了具有背压功能的异步组件之间的交互。例如，一个数据仓库（充当Publisher）可以生成数据，HTTP 服务器（充当Subscriber）可以将这些数据写入响应。Reactive Streams 的主要目的是让订阅者控制发布者产生数据的速度，即控制其快慢。

    常见问题：如果发布者无法减速怎么办？
    Reactive Streams 的目的仅仅是建立机制和边界。 如果发布者无法减速，它必须决定是进行缓冲、丢弃数据还是失败。

    响应式 API

    Reactive Streams 在互操作性方面发挥着重要作用。它对库和基础设施组件很有吸引力，但作为应用程序 API 则用处较小，因为其层级过低。应用程序需要更高级、功能更丰富的 API 来组合异步逻辑——类似于 Java 8 的 Stream API，但不止限于集合。这正是响应式库所扮演的角色。

    Reactor 是 Spring WebFlux 的首选响应式库。它提供了 Mono 和 Flux API 类型，用于处理 0..1 (Mono) 和 0..N (Flux) 的数据序列，并配备了一套与 ReactiveX 操作符词汇表 对齐的丰富操作符集。Reactor 是一个响应式流库，因此其所有操作符都支持非阻塞背压。Reactor 专注于服务端 Java，并与 Spring 紧密协作开发。

    WebFlux 将 Reactor 作为核心依赖，但通过 Reactive Streams 与其他响应式库互操作。通常，WebFlux API 接受一个普通的 Publisher 作为输入，在内部将其适配为 Reactor 类型并使用它，然后返回 Flux 或 Mono 作为输出。因此，您可以传入任何 Publisher 作为输入并对输出应用操作，但您需要将输出适配以便在其他响应式库中使用。只要可行（例如在注解控制器中），WebFlux 就会透明地适配 RxJava 或其他响应式库的使用。有关更多详细信息，请参阅 响应式库。

    除了 Reactive API 之外，WebFlux 还可以与 Kotlin 中的 Coroutines API 一起使用，后者提供了一种更命令式的编程风格。 接下来将提供使用 Coroutines API 的 Kotlin 代码示例。

    编程模型

    spring-web 模块包含 Spring WebFlux 所依赖的响应式基础，包括 HTTP 抽象、针对支持的服务器的 Reactive Streams 适配器、编解码器，以及一个与 Servlet API 相当但具有非阻塞契约的核心 WebHandler API。

    在此基础上，Spring WebFlux 提供了两种编程模型可供选择：

    • Annotated Controllers：与 Spring MVC 一致，并基于来自spring-web模块的相同注解。Spring MVC 和 WebFlux 控制器均支持响应式（Reactor 和 RxJava）返回类型，因此很难将它们区分开来。一个显著的区别是，WebFlux 还支持响应式@RequestBody参数。

    • Functional Endpoints：基于 Lambda 的轻量级函数式编程模型。您可以将其视为应用程序用于路由和处理请求的小型库或工具集。与注解控制器相比，主要区别在于应用程序从头到尾负责请求处理，而不是通过注解声明意图并等待回调。

    Applicability

    Spring MVC 还是 WebFlux？

    一个自然的问题，但它建立了一个不合理的二元对立。实际上，两者协同工作以扩大可用选项的范围。这两者旨在保持相互间的连续性和一致性，它们并行提供，且来自一方的反馈使双方受益。下图展示了这两者的关系、共同点以及各自独特的支持内容：

    我们建议您考虑以下具体要点：

    • 如果您的 Spring MVC 应用程序运行正常，则无需更改。命令式编程是编写、理解和调试代码的最简单方式。由于历史上大多数库都是阻塞的，因此您拥有最大的库选择范围。

    • 如果您正在为非阻塞 Web 栈选购方案，Spring WebFlux 不仅提供与同类技术相同的执行模型优势，还提供了多种服务器选择（Netty、Tomcat、Jetty 和 Servlet 容器）、多种编程模型选择（注解式控制器和功能型 Web 端点）以及多种响应式库选择（Reactor、RxJava 或其他）。

    • 如果您有兴趣使用 Java 8 lambda 或 Kotlin 的轻量级、功能型 Web 框架，可以使用 Spring WebFlux 的功能型 Web 端点。对于需求较为简单的小型应用程序或微服务而言，这也是一个不错的选择，因为它们可以从更高的透明度和控制中受益。

    • 在微服务架构中，您可以混合使用带有 Spring MVC 或 Spring WebFlux 控制器的应用程序，或者带有 Spring WebFlux 函数式端点的应用程序。在这两个框架中都支持相同的基于注解的编程模型，使得更容易复用知识，同时也便于为不同的任务选择合适的工具。

    • 评估应用程序的一种简单方法是检查其依赖项。如果您需要使用阻塞式持久化 API（如 JPA、JDBC）或网络 API，那么对于常见架构而言，Spring MVC 至少是最佳选择。虽然技术上可以使用 Reactor 和 RxJava 在单独的线程上执行阻塞调用，但这样无法充分利用非阻塞 Web 堆栈的优势。

    • 如果您拥有调用远程服务的 Spring MVC 应用程序，请尝试使用响应式 WebClient。您可以直接从 Spring MVC 控制器方法返回响应式类型（Reactor、RxJava、或其他）。每次调用的延迟越高或调用之间的相互依赖性越强，其带来的收益就越显著。Spring MVC 控制器也可以调用其他响应式组件。

    • 如果您拥有庞大的团队，请注意向非阻塞、函数式和声明式编程转变时的陡峭学习曲线。在不进行完全切换的情况下开始实践的一种方法是使用响应式 WebClient。除此之外，从小处着手并衡量其收益。我们预计，对于广泛的应用程序而言，这种转变是不必要的。如果您不确定要寻找哪些收益，请从了解非阻塞 I/O 的工作原理（例如单线程 Node.js 上的并发）及其影响开始。

    Servers

    Spring WebFlux 支持 Tomcat、Jetty、Servlet 容器，以及 Netty 等非 Servlet 运行时。所有服务器都适配了底层通用 API，以便跨服务器支持更高级别的编程模型。

    Spring WebFlux 没有内置支持来启动或停止服务器。但是，它很容易通过 Spring 配置和 组装 WebFlux 基础设施以及 运行 应用程序，只需几行代码即可。

    Spring Boot 提供了一个 WebFlux starter，可自动化这些步骤。默认情况下，starter 使用 Netty，但通过更改 Maven 或 Gradle 依赖项，可以轻松切换到 Tomcat 或 Jetty。Spring Boot 默认使用 Netty，因为它在异步、非阻塞领域应用更广泛，并允许客户端和服务器共享资源。

    Tomcat 和 Jetty 既可以与 Spring MVC 一起使用，也可以与 WebFlux 一起使用。但请注意，它们的使用方式非常不同。Spring MVC 依赖于 Servlet 阻塞式 I/O，并允许应用程序在需要时直接使用 Servlet API。Spring WebFlux 依赖于 Servlet 非阻塞式 I/O，并通过低级适配器使用 Servlet API，该 API 不直接暴露以供使用。

    强烈建议在 WebFlux 应用程序上下文中不要映射 Servlet 过滤器或直接操作 Servlet API。 由于上述原因，在同一上下文中混合阻塞 I/O 和非阻塞 I/O 会导致运行时问题。

    Performance

    性能具有多种特征和含义。响应式和非阻塞通常不会使应用程序运行得更快。在某些情况下——例如，使用WebClient并行执行远程调用时——它们可能会提升性能。然而，采用非阻塞方式需要更多的工作量，这可能会略微增加所需的处理时间。

    反应式和非阻塞的关键预期优势在于能够使用少量固定数量的线程和更少的内存进行扩展。这使得应用程序在负载下更具弹性，因为它们以更可预测的方式扩展。然而，为了观察到这些优势，您需要拥有一定的延迟（包括慢速且不可预测的网络 I/O 混合）。正是在这里，反应式堆栈开始展现其优势，差异可能非常显著。

    并发模型

    Spring MVC 和 Spring WebFlux 都支持注解控制器，但在并发模型以及对阻塞和线程的默认假设方面存在关键差异。

    在 Spring MVC（以及一般的 Servlet 应用程序）中，假定应用程序可以阻塞当前线程（例如用于远程调用）。因此，Servlet 容器使用大型线程池来吸收请求处理期间可能出现的阻塞。

    在 Spring WebFlux（以及通用的非阻塞服务器）中，假定应用程序不会阻塞。因此，非阻塞服务器使用一个小型、固定大小的线程池（事件循环工作线程）来处理请求。

    “可扩展”和“少量线程”听起来可能相互矛盾，但永远不阻塞当前线程（而是依赖回调）意味着您不需要额外的线程，因为没有需要吸收的阻塞调用。

    调用阻塞式 API

    如果您确实需要使用阻塞库怎么办？Reactor 和 RxJava 都提供了 publishOn 算子，以便在不同的线程上继续处理。这意味着有一个简单的逃生通道。然而，请记住，阻塞 API 并不适合这种并发模型。

    可变状态

    在 Reactor 和 RxJava 中，您通过操作符声明逻辑。在运行时，会形成一个响应式管道，数据在其中按顺序、分阶段进行处理。这一关键优势在于，它使应用程序无需保护可变状态，因为该管道内的应用程序代码永远不会并发调用。

    线程模型

    在运行 Spring WebFlux 的服务器上，您应该看到哪些线程？

    • 在“原生”Spring WebFlux 服务器（例如，没有数据访问或其他可选依赖）上，您可以预期有一个用于服务器的线程和几个用于请求处理的线程（通常与 CPU 核心数一样多）。然而，Servlet 容器可能会启动更多线程（例如 Tomcat 上的 10 个），以支持 Servlet（阻塞）I/O 和 Servlet 3.1（非阻塞）I/O 的使用。

    • 响应式WebClient采用事件循环模式运行。因此，您可以看到与之相关的少量固定数量的处理线程（例如，使用 Reactor Netty 连接器时的reactor-http-nio-）。然而，如果 Reactor Netty 同时用于客户端和服务器，则默认情况下两者共享事件循环资源。

    • Reactor 和 RxJava 提供了名为调度器（scheduler）的线程池抽象，用于配合 `publishOn` 操作符以将处理切换到不同的线程池。这些调度器的名称暗示了特定的并发策略——例如，“parallel”（用于具有有限线程数的 CPU 密集型工作）或“elastic”（用于具有大量线程的 I/O 密集型工作）。如果您看到此类线程，这意味着某些代码正在使用特定的线程池 `Scheduler` 策略。

    • 数据访问库和其他第三方依赖项也可以创建并使用它们自己的线程。

    Configuring

    Spring Framework 不提供启动和停止服务器的支持。要配置服务器的线程模型，您需要使用特定于服务器的配置 API，或者如果您使用的是 Spring Boot，请检查每个服务器的 Spring Boot 配置选项。您可以直接配置WebClient。对于其他所有库，请参阅其各自的文档。
