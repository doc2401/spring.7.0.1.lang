    使用 Spring JMS

    本节介绍如何使用 Spring 的 JMS 组件。

    JmsTemplate and JmsClient

    JmsTemplate 类是 JMS 核心包中的中心类。它简化了 JMS 的使用，因为它在发送或同步接收消息时处理资源的创建和释放。

    JmsClient 是 Spring Framework 7.0 中的新 API 变体，其设计遵循了JdbcClient等组件的模式。JmsClient基于JmsTemplate构建，用于实现简单的发送和接收操作，并支持针对每个操作进行自定义配置。

    Using JmsTemplate

    使用 JmsTemplate 的代码只需实现回调接口，这些接口为其提供了定义明确的高级契约。MessageCreator 回调接口在接收到由调用代码提供的、来自 JmsTemplate 的 Session 时创建消息。为了支持更复杂的 JMS API 用法，SessionCallback 提供 JMS session，而 ProducerCallback 则暴露了 Session 和 MessageProducer 对。

    JMS API 暴露了两种类型的发送方法：一种将交付模式、优先级和生存时间作为服务质量 (QOS) 参数，另一种不接收任何 QOS 参数并使用默认值。由于 `JmsTemplate` 拥有许多发送方法，因此将设置 QOS 参数暴露为 bean 属性，以避免发送方法数量的重复。同样，同步接收调用的超时值是通过使用 `setReceiveTimeout` 属性来设置的。

    某些 JMS 提供者允许通过配置 ConnectionFactory 在管理上设置默认 QOS 值。这会导致调用 MessageProducer 实例的 send 方法（send(Destination destination, Message message)）时，使用的 QOS 默认值与 JMS 规范中指定的不同。为了提供一致的 QOS 值管理，因此必须显式启用 JmsTemplate 使用其自身的 QOS 值，方法是设置布尔属性 isExplicitQosEnabled 为 true。

    为了方便起见，JmsTemplate 还提供了一个基本的请求 - 回复操作，允许发送消息并等待在作为该操作一部分创建的临时队列上的回复。

    配置后的 JmsTemplate 类实例是线程安全的。这一点很重要，因为它意味着您可以配置单个 JmsTemplate 实例，然后安全地将此共享引用注入到多个协作对象中。明确地说，JmsTemplate 是有状态的，因为它维护对 ConnectionFactory 的引用，但这种状态不是对话状态。

    Using JmsClient

    自 Spring Framework 4.1 起，JmsMessagingTemplate 构建于 JmsTemplate 之上，并提供了与 Spring 通用消息抽象的集成——即处理用于发送和接收的 org.springframework.messaging.Message，抛出 org.springframework.messaging.MessagingException，并通过 org.springframework.messaging.converter.MessageConverter 进行负载转换（提供许多常见的转换器实现）。

    自 Spring Framework 7.0 起，提供了一个名为 JmsClient 的流式 API。它提供了围绕 org.springframework.messaging.Message 的可定制操作以及抛出 org.springframework.messaging.MessagingException 的功能，类似于 JmsMessagingTemplate，同时还集成了 org.springframework.messaging.converter.MessageConverter。JmsClient 可以针对给定的 `ConnectionFactory` 或给定的 JmsTemplate 创建，在后一种情况下默认会复用其设置。有关使用示例，请参阅 JmsClient。

    Connections

    JmsTemplate 需要一个 ConnectionFactory 引用。ConnectionFactory 是 JMS 规范的一部分，也是使用 JMS 的入口点。客户端应用程序将其用作工厂来创建与 JMS 提供者的连接，并封装各种配置参数，其中许多是特定于供应商的，例如 SSL 配置选项。

    在 EJB 中使用 JMS 时，供应商提供 JMS 接口的实现，以便它们能够参与声明式事务管理并执行连接和会话的池化。为了使用该实现，Jakarta EE 容器通常要求您在 EJB 或 servlet 部署描述符中将 JMS 连接工厂声明为 resource-ref。为了确保在 EJB 内部使用 JmsTemplate 时能够利用这些功能，客户端应用程序应确保其引用了 ConnectionFactory 的管理实现。

    缓存消息资源

    标准 API 涉及创建许多中间对象。要发送消息，需执行以下"API"遍历：

    ConnectionFactory->Connection->Session->MessageProducer->send

    在ConnectionFactory和Send操作之间，会创建并销毁三个中间对象。为了优化资源使用并提高性能，Spring 提供了两种ConnectionFactory的实现。

    Using SingleConnectionFactory

    Spring 提供了 ConnectionFactory 接口的一个实现，即 SingleConnectionFactory。该实现在所有 createConnection() 调用中返回相同的 Connection，并忽略对 close() 的调用。这在测试和独立环境中非常有用，因为可以使用同一个连接来处理多个可能跨越任意数量事务的 JmsTemplate 调用。SingleConnectionFactory 引用了一个标准的 ConnectionFactory，该连接工厂通常来自 JNDI。

    Using CachingConnectionFactory

    CachingConnectionFactory 扩展了 SingleConnectionFactory 的功能，并增加了对 Session、MessageProducer 和 MessageConsumer 实例的缓存。初始缓存大小设置为 1。您可以使用 sessionCacheSize 属性来增加缓存的会话数量。请注意，实际缓存的会话数量会多于该数值，因为会话是根据其确认模式进行缓存的；因此，当 sessionCacheSize 设置为 1 时，最多可能有四个缓存的会话实例（每种确认模式各一个）。MessageProducer 和 MessageConsumer 实例在其所属会话中进行缓存，并且在缓存时也会考虑生产者和消费者的唯一属性。MessageProducers 根据其目标进行缓存。MessageConsumers 则根据由目标、选择器、noLocal 传递标志以及持久订阅名称（如果创建持久消费者）组成的键进行缓存。

    用于临时队列和主题 (TemporaryQueue/TemporaryTopic) 的 MessageProducers 和 MessageConsumers 永远不会被缓存。不幸的是，WebLogic JMS 恰好在其常规目标实现上实现了临时队列/主题接口，错误地表明其所有目标都无法被缓存。请在 WebLogic 上使用不同的连接池/缓存，或针对 WebLogic 自定义 CachingConnectionFactory。

    目标管理

    作为 ConnectionFactory 实例，目的地是可以在 JNDI 中存储和检索的 JMS 管理对象。在配置 Spring 应用程序上下文时，您可以使用 JNDI JndiObjectFactoryBean 工厂类或 <jee:jndi-lookup> 来执行对对象引用的 JMS 目的地依赖注入。然而，如果应用程序中有大量目的地，或者存在 JMS 提供者特有的高级目的地管理功能时，这种策略通常很繁琐。此类高级目的地管理的示例包括动态目的地的创建或对目的地分层命名空间的支持。JmsTemplate 将目的地名称的解析委托给实现 DestinationResolver 接口的 JMS 目的地对象。DynamicDestinationResolver 是 JmsTemplate 使用的默认实现，并支持解析动态目的地。此外还提供了 JndiDestinationResolver，作为包含在 JNDI 中的目的地的服务定位器，并可选择回退到 DynamicDestinationResolver 中包含的行为。

    在 JMS 应用中，经常只有在运行时才知道使用的目的地，因此无法在部署应用程序时通过管理方式创建这些目的地。这通常是因为相互作用的系统组件之间存在共享的应用程序逻辑，它们根据众所周知的命名约定在运行时创建目的地。尽管动态目的地的创建不属于 JMS 规范的一部分，但大多数供应商都提供了此功能。动态目的地使用用户定义的名称创建，这使它们与临时目的地区分开来，并且通常不会注册到 JNDI 中。由于与目的地关联的属性因供应商而异，因此用于创建动态目的地的 API 也因供应商而异。然而，供应商有时会做出的一个简单实现选择是忽略 JMS 规范中的警告，并使用 TopicSession 的 createTopic(String topicName) 方法或 QueueSession 的 createQueue(String queueName) 方法来创建具有默认目的地属性的新目的地。根据供应商的实现，DynamicDestinationResolver 也可以创建一个物理目的地，而不仅仅是解析一个。

    pubSubDomain 布尔属性用于配置 JmsTemplate，使其了解所使用的 JMS 域。默认情况下，该属性的值为 false，表示将使用点对点域（Queues）。此属性（由 JmsTemplate 使用）通过实现 DestinationResolver 接口来确定动态目标解析的行为。

    您还可以通过属性defaultDestination为JmsTemplate配置默认目标。默认目标用于不引用特定目标的发送和接收操作。

    消息监听器容器

    在 EJB 世界中，JMS 消息最常见的用途之一是驱动消息驱动的 Bean（MDBs）。Spring 提供了解决方案，以创建消息驱动的 POJO（MDP），而无需将用户绑定到 EJB 容器。（有关 Spring MDP 支持的详细说明，请参阅 异步接收：消息驱动 POJO。）端点方法可以使用@JmsListener注解——有关更多详细信息，请参阅基于注解的监听器端点。

    消息监听器容器用于从 JMS 消息队列接收消息，并驱动注入到其中的 MessageListener。监听器容器负责消息接收的所有线程调度以及向监听器分发消息以供处理。消息监听器容器是 MDP 与消息提供者之间的中介，负责注册接收消息、参与事务、资源的获取与释放、异常转换等任务。这使得您可以编写（可能复杂的）与接收消息（并可能对此做出响应）相关的业务逻辑，而将样板式的 JMS 基础设施关注点委托给框架处理。

    Spring 包中提供了两个标准的 JMS 消息监听器容器，每个容器都有其专用的功能集。

    • SimpleMessageListenerContainer

    • DefaultMessageListenerContainer

    Using SimpleMessageListenerContainer

    此消息监听器容器是两种标准形式中较简单的一种。它在启动时创建固定数量的 JMS 会话和消费者，通过使用标准的 JMS MessageConsumer.setMessageListener() 方法注册监听器，并将监听器回调的执行交由 JMS 提供者处理。此变体不支持根据运行时需求进行动态调整，也不支持参与外部管理的事务。在兼容性方面，它非常贴近独立 JMS 规范的精神，但通常与 Jakarta EE 的 JMS 限制不兼容。

    虽然 SimpleMessageListenerContainer 不支持参与外部管理的事务，但它确实支持原生的 JMS 事务。要启用此功能，您可以将 sessionTransacted 标志切换为 true，或者在 XML 命名空间中设置 acknowledge 属性为 transacted。此时，监听器抛出的异常将导致回滚，消息会被重新投递。或者，可以考虑使用 CLIENT_ACKNOWLEDGE 模式，该模式在发生异常时也能提供重新投递功能，但不使用事务性 Session 实例，因此不会将任何其他 Session 操作（例如发送响应消息）包含在事务协议中。
    默认的 AUTO_ACKNOWLEDGE 模式无法提供适当的可靠性保证。当监听器执行失败时，消息可能会丢失（因为提供者会在调用监听器后自动确认每条消息，不会向提供者传播任何异常），或者当监听器容器关闭时（您可以通过设置 acceptMessagesWhileStopping 标志来配置此行为）。如果存在可靠性需求（例如用于可靠的队列处理和持久化主题订阅），请确保使用事务性会话。

    Using DefaultMessageListenerContainer

    此消息监听器容器在大多数情况下使用。与SimpleMessageListenerContainer相比，该容器变体允许动态适应运行时需求，并能够参与外部管理的事务。当配置了JtaTransactionManager时，每个接收到的消息都会注册到 XA 事务中。因此，处理过程可以利用 XA 事务语义。此监听器容器在 JMS 提供商的低要求、高级功能（例如参与外部管理的事务）以及与 Jakarta EE 环境的兼容性之间取得了良好的平衡。

    您可以自定义容器的缓存级别。请注意，当未启用缓存时，每次接收消息都会创建一个新的连接和一个新的会话。将此与非持久订阅和高负载相结合可能会导致消息丢失。在这种情况下，请确保使用适当的缓存级别。

    该容器在代理宕机时还具有可恢复功能。默认情况下，简单的 BackOff 实现每五秒重试一次。您可以指定自定义的 BackOff 实现以获取更细粒度的恢复选项。有关示例，请参阅 ExponentialBackOff。

    与它的兄弟类 (SimpleMessageListenerContainer) 类似，DefaultMessageListenerContainer 支持原生的 JMS 事务，并允许自定义确认模式。如果您的场景可行，强烈建议使用此方式而非外部管理的事务——也就是说，如果您可以接受在 JVM 意外终止时偶尔出现重复消息的情况。您可以在业务逻辑中实现自定义的重复消息检测步骤来处理此类情况——例如，通过检查业务实体是否存在或检查协议表来实现。任何此类安排都比替代方案（即通过配置 JtaTransactionManager 来包装您的整个处理过程，以涵盖 JMS 消息的接收以及在消息监听器中执行业务逻辑（包括数据库操作等））要高效得多。
    默认的 AUTO_ACKNOWLEDGE 模式无法提供适当的可靠性保证。当监听器执行失败时，消息可能会丢失（因为提供者会在调用监听器后自动确认每条消息，不会向提供者传播任何异常），或者当监听器容器关闭时（您可以通过设置 acceptMessagesWhileStopping 标志来配置此行为）。如果存在可靠性需求（例如用于可靠的队列处理和持久化主题订阅），请确保使用事务性会话。

    事务管理

    Spring 提供了一个 JmsTransactionManager，用于管理单个 JMS ConnectionFactory 的事务。这使得 JMS 应用程序能够利用 Spring 的托管事务功能，如数据访问章节中的事务管理部分所述。JmsTransactionManager 执行本地资源事务，将来自指定 ConnectionFactory 的 JMS Connection/Session 对绑定到线程。JmsTemplate 会自动检测此类事务性资源并相应地对其操作。

    在 Jakarta EE 环境中，ConnectionFactory 会连接池化 Connection 和 Session 实例，从而在不同事务之间高效地重用这些资源。在独立环境中，使用 Spring 的 SingleConnectionFactory 会导致共享 JMS Connection，而每个事务拥有自己独立的 Session。或者，可以考虑使用特定于提供者的连接池适配器，例如 ActiveMQ 的 PooledConnectionFactory 类。

    您也可以使用 JmsTemplate 配合 JtaTransactionManager 和具有 XA 功能的 JMS ConnectionFactory 来执行分布式事务。请注意，这需要同时使用 JTA 事务管理器以及正确配置为 XA 的 ConnectionFactory。（请查阅您的 Jakarta EE 服务器或 JMS 提供程序的文档。）

    在跨托管和非托管事务环境重用代码时，如果使用 JMS API 从 Connection 创建 Session，可能会令人困惑。这是因为 JMS API 只有一个用于创建 Session 的工厂方法，并且它需要指定事务和确认模式值。在托管环境中，设置这些值由环境的事务基础设施负责，因此供应商对 JMS Connection 的包装器会忽略这些值。在非托管环境中使用 JmsTemplate 时，您可以通过使用属性 sessionTransacted 和 sessionAcknowledgeMode 来指定这些值。当将 PlatformTransactionManager 与 JmsTemplate 一起使用时，模板始终会获得一个事务性的 JMS Session。
